동기화 상태 반영 최대 30초 → 중앙값 0.14초
문제
각 기기가 30초 주기 heartbeat로만 상태를 읽어, 폰에서 시작된 개입이 PC에 최대 30초 늦게 반영됐습니다.
해결
서버가 단계 변경을 받는 즉시 같은 세션의 다른 기기로 WebSocket push하도록 바꾸고, 변경·수신·전송 시각을 메시지에 실어 지연을 잴 수 있게 했습니다.
결과
운영 서버(싱가포르 ↔ 한국) 10회 측정 중앙값 0.135초, 최대 0.32초. 남은 지연은 네트워크 왕복 시간입니다.
정합성 기기마다 다른 시계를 서버 기준으로 통일
문제
기기가 보낸 상태 시작 시각이 각자의 시계 기준이라, 서버에서 합산한 집중·딴짓 시간이 몇 초씩 어긋났습니다.
해결
heartbeat에 기기 현재 시각을 싣고 서버 수신 시각 − 기기 시각만큼 보정했습니다. 사용자 교정("딴짓 아니야")은 새 분기 없이 기존 구간 자르기 규칙으로 처리했습니다.
결과
여러 기기의 시간을 서버 한 곳에서 계산하고, 시계 차이·교정 케이스를 API 테스트로 고정했습니다.
연결 앱이 꺼진 기기를 10초 안에 비활성으로 감지
문제
90초 heartbeat로만 생존을 판단해, 앱을 꺼도 다른 기기에는 한동안 연결된 것으로 보였습니다.
해결
WebSocket 연결을 생존 신호로 쓰고, 연결이 모두 끊긴 뒤 10초 유예가 지나면 비활성을 push했습니다. 유예 안의 재연결은 알리지 않아 순간 끊김에 흔들리지 않습니다.
결과
실제 WebSocket을 여닫는 통합 테스트로 유예·재연결 시나리오를 검증했습니다.

팀 운영: 모노레포와 shared/ 단일 출처(상태·API 스키마)를 두고 "코드를 바꾸면 같은 PR에서 문서도 고친다"는 규칙을 세워, 3개 클라이언트가 같은 계약으로 개발되게 했습니다. 저장소는 팀 결정으로 비공개입니다.

2026.10 – 11 · 5인 팀 · 사용자·관리자 API 담당

경희 공간찾기 모임 조건에 맞는 교내 공간 추천

인원·소음·콘센트 조건으로 교내 공간을 찾는 서비스입니다. API 10여 개를 기능·테스트·규칙 문서 순으로 구현했고, 운영 서버 부하 테스트에서 목표 60 RPS를 p99 163ms로 통과했습니다.

  • Java 21
  • Spring Boot 4
  • JPA
  • PostgreSQL
  • Flyway
  • AWS
동시성 비관적 잠금으로 관리자 처리 결과가 지워지는 경합 차단
문제
관리자가 재조사 요청을 처리하는 순간 사용자가 같은 요청을 다시 저장하면, 공개된 처리 결과의 연결이 지워질 수 있었습니다. 테스트 케이스를 먼저 쓰다가 발견했습니다.
해결
대기 요청 조회에 PESSIMISTIC_WRITE 잠금을 걸어 사용자 저장이 처리 완료를 기다리게 했습니다. 처리된 요청은 대기 상태로 조회되지 않으므로 이후 저장은 새 요청이 됩니다.
정합성 저장 응답과 재조회 응답의 시각 불일치를 4개 API에서 제거
원인
Java는 나노초 단위로 시각을 만들지만 PostgreSQL은 마이크로초까지만 저장합니다.
해결
저장 시각을 truncatedTo(MICROS)로 DB 정밀도에 맞추고, 같은 패턴이 있던 4개 API에 모두 적용했습니다.

운영 CORS로 보였던 로그인 500의 실제 원인 찾기
원인
Secrets Manager에 잘못 등록된 DB 키였습니다. 증상만 보고 CORS를 의심해 시간을 썼고, 로그로 범위를 좁힌 뒤에야 찾았습니다.
해결
키를 교체하고 "없는 이메일로 로그인해 500이면 키·DB 문제, 401이면 정상"이라는 판별법을 운영 문서에 남겼습니다.
인증 15분마다 강제 로그아웃되던 문제 해결
원인
http 프론트와 다른 도메인 API 사이에서 Secure 쿠키가 전송되지 않아 토큰 재발급이 실패했습니다.
해결
쿠키는 유지한 채 X-Refresh-Token 헤더로도 재발급받을 수 있게 했습니다.
